# Decision Log — RC Airplane Build Planner PRD

## Initial product intent
- Build a browser-based application for selecting RC airplane components, checking their compatibility, and showing overall specifications for a completed build.
- 2026-10-24 — Product owner clarified the demo needs wind-response motion: calm wind gives a straight path, slight crosswind angles the aircraft/path, and strong wind carries the aircraft away. Add visible landscape/path context and describe the behavior as a scripted illustration, not validated aircraft physics.
- 2026-10-24 — Product owner asked whether flight pace reflects the configured Build. Use the supported synthetic static thrust-to-weight estimate to vary illustrative travel pace; show neutral motion when unavailable. Do not claim real speed, climb, or aerodynamic predictions.
- 2026-10-24 — Add four selectable preview presets to demonstrate low, baseline, high, and unavailable propulsion references; presets use explicitly synthetic motor/battery data and update the in-preview build.
- 2026-10-24 — Add synthetic receiver-range data and a weak-range demo profile. The preview should show accumulated distance, announce signal loss beyond the mock receiver range, and let reloading a demo profile reset the scenario.

## Decisions and working assumptions
- 2026-10-24 — Create a PRD; the project contains no existing PRD, BMad project configuration, or product inputs beyond its README and the user's brief. Use the default planning-artifact location `_bmad-output/planning-artifacts/prds/`.
- 2026-10-24 — Calibrate the artifact for a hobby/hackathon prototype.
- 2026-10-24 — Use the Fast path. The user supplied no extra inputs and asked for best assumptions for the remaining gaps.
- 2026-10-24 — Treat “simulator” as a fixed-wing build planner that checks components and summarizes a Build. Exclude real-time flight simulation and side-by-side Build comparison for this prototype; the user did not specify flight physics, gameplay, or variant comparison.
- 2026-10-24 — Assume a curated Catalog with Airframe, motor, propeller, ESC, battery, servo, and receiver roles; no retailer integration, user-authored parts, accounts, cloud persistence, or sharing in the prototype.
- 2026-10-24 — Use three Compatibility results: compatible, incompatible, and needs-check. A known limit violation is incompatible; missing or unvalidated data yields needs-check. No borderline warning threshold is assumed.
- 2026-10-24 — Define the first demo rule set for voltage, current, battery discharge, Airframe mass, physical fit, and control capacity. Use clearly labeled synthetic validation fixtures with explicit formulas and expected outcomes; do not present these values as real hardware recommendations.
- 2026-10-24 — Require manufacturer-backed Catalog sources before real Components replace validation fixtures.
- 2026-10-24 — Separate competitive landscape research into `addendum.md`. A close direct comparable exists, so the hackathon PRD makes no novelty claim; no differentiator is required unless the goal changes to public-product positioning.
