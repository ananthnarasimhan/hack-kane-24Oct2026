| Original Text | Revised Text | Changes |
|---------------|--------------|---------|
| §1 Vision: “As the builder selects Components, the planner checks known fit and electrical constraints…” | “As the builder selects Components, the planner checks known compatibility constraints…” | The current phrase mentions only fit and electrical checks, while the requirements also cover mass and control constraints. Use an umbrella phrase that reflects the listed checks. |
| §3 Glossary: “Airframe — The fixed-wing structure, with required Component roles and published limits.” / “Component — A selectable Airframe, motor, propeller, electronic speed controller (ESC), battery, servo, or receiver.” | “Consider: Clarify whether an Airframe is itself a Component role or the base item that receives the other Components.” | The definitions classify Airframe both as the structure that has required roles and as a selectable Component. The intended product model is unclear from these definitions. |
| FR-2: “The planner can evaluate the Airframe, powertrain, physical-fit, and control requirements listed below.” | “The planner can evaluate the electrical, motor/propeller, Airframe-mass, physical-fit, and control requirements listed below.” | “Powertrain” is not defined and does not make clear which requirements are included. Naming the requirement groups matches the checks that follow. |
| FR-2 Current check: “Its current must not exceed motor maximum or ESC continuous-current ratings; battery continuous discharge current (`capacity in Ah × continuous C rating`) must be at least that current.” | “The reference current must not exceed the motor’s maximum current or the ESC’s continuous-current rating. The battery’s continuous discharge current (`capacity in Ah × continuous C rating`) must be at least the reference current.” | Replaces the ambiguous “Its” and “that current” references with the named reference current, and makes the comparison limits explicit. |
| FR-3: “Each result shows the rule, selected values, applicable limit, or missing input.” | “Each result names the rule and selected values, and shows the applicable limit or identifies the missing input.” | The original “or” can read as though a result may omit the rule or selected values. The revision states which information is always shown and which is conditional. |
| Validation fixture: “A 279 mm propeller yields incompatible; a missing battery C rating yields needs-check.” | “With a 279 mm propeller, the compatibility result is incompatible. Without the battery’s continuous C rating, the result is needs-check.” | Adds the missing object after each outcome so readers can tell what is incompatible or needs checking. |
| §7 Trust and safety: “The planner must not label an incomplete or data-poor Build as safe.” | “The planner must not label an incomplete Build or a Build with incomplete Catalog data as safe.” | Replaces “data-poor,” which is not defined elsewhere, with the specific condition described in the requirements. |
| §8 SM-C1: “The prototype produces zero false compatible outcomes for known-invalid or data-incomplete fixtures.” | “The prototype marks no known-invalid or data-incomplete fixture as compatible.” | Rephrases the double-negative-style metric as a direct, testable condition. |
| §6.2: “The §5 Non-Goals also apply to the MVP. Additional deferrals:” | “The non-goals in §5 also apply to the MVP. Additional deferrals are:” | Makes the cross-reference read as a complete sentence and clarifies the transition to the list. |
